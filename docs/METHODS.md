# Methods

## Design principles

AtmosCoder-Bench was built under two constraints that shape every stage described below. First, ground truth is execution-grounded: every problem is paired with an executable reference solver whose output defines the accepted answer, so that the released corpus can be re-verified end to end without a single model call. Second, construction follows a propose-and-verify architecture: large language models (LLMs) act only as proposers of candidate solvers, answers and rewordings, whereas admission is decided by gates that do not depend on trusting any single model, namely deterministic execution, anchoring to the textbook's printed answer, agreement across models from three different developers, and adjudication by a domain expert. No artefact enters the corpus on a model's judgement alone. The points at which a human decides are enumerated in the section Human expert involvement below; the models used as construction tools and the models evaluated as subjects are listed, with their exact API identifiers, in the two closing sections.

## Construction of the core problem set

The full pipeline is summarized in Fig. 1.

**Source curation.** Thirteen undergraduate and graduate textbooks in atmospheric science and air quality were digitized from PDF to structured Markdown using a hosted document-parsing service (MinerU), with formula and table recognition enabled. GPT-5.5 then read each digitized book page by page, end to end, and recorded every exercise verbatim together with its source (book and chapter), so that coverage is exhaustive rather than sampled. A second model from a different developer, Claude Opus 4.8, screened each extracted item for eligibility: the statement had to be solvable from its own text (no reference to external figures, tables, datasets or neighbouring exercises), had to ask for a numeric quantity, had to be free of OCR corruption, and had to state every input its solution requires. Only items surviving both passes became candidate problems.

**The executable solver contract.** For every candidate a `solve()` function was synthesized under a strict contract: (i) every value given in the problem becomes a function parameter carrying its stated value as a default; (ii) only the Python standard library may be used; (iii) all unit conversions are performed explicitly in code; and (iv) the return value is a dictionary with one entry per asked quantity, in the order asked, each holding a numeric value and a unit string. Solvers were authored blind, in that no model was ever shown the value of the answer, and were retained only if they executed. The solver released with each problem is the one authored by a single pre-designated model (Claude Opus 4.8), so release quality is uniform and no post-hoc selection among agreeing solvers occurs; because admission requires all solutions to agree (below), the frozen ground-truth value does not depend on this choice.

**Answer verification.** The verification route is a property of the source book and was decided first: does the textbook publish an answer? Both routes are three-way. The same three frontier models, one per developer (Claude Opus 4.8, GPT-5.5 and Gemini 3.1 Pro), each independently wrote and ran an executable solver from the problem text alone. No model was shown the answer's value; on the textbook-anchored route each was told only the answer's units and count, so that a correct derivation reported in SI units remains commensurable with a book answer expressed in mixed units. Where the textbook publishes an answer, a problem was admitted only when all three solutions matched it within the same 5% relative tolerance later used at evaluation (defined in Grading below); disagreement between the models and the book exposed misprinted keys (corrected and logged as errata), and disagreement among the models exposed damaged extractions (repaired or discarded). Where no published answer exists, a problem was admitted only when all three solutions agreed with one another, sub-question by sub-question, and the agreed value became the reference. In both routes the agreed computation was then re-checked by hand by a domain expert, who reproduced the derivation from the problem statement and confirmed that the physics, the units and the number of asked quantities were consistent with the solver, before the value was frozen as ground truth. Model agreement therefore proposes a ground truth; a person accepts it.

**Quality control.** The admitted pool was audited for ill-posedness with automated rule-based checks (answers hard-coded into a solver, duplicate answer keys that collapse under grading, and answer labels that mismatch the question) and with a three-model consensus review of well-posedness. Because LLM auditors over-flag, automated and consensus flags only raised suspects and never decided an outcome: a domain expert adjudicated every flag, and confirmed defects were repaired and re-verified or removed together with their variants. A separate two-model value audit (GPT-5.5 flags, Claude Opus 4.8 confirms) removed low-value items such as single-step plug-ins and pure unit conversions, reducing a larger extraction pool to the released set.

**Difficulty calibration by de-scaffolding.** Textbook statements frequently hand over knowledge a competent solver should already possess. Core problems therefore underwent a two-pass de-scaffolding that removed, first, ready-made solving formulas quoted in the statement and, second, recallable physical constants and canonical definitions, while preserving every problem-specific input, unit and disambiguating assumption. Each candidate edit was admitted only if it survived a triple gate: the editing model reproduced the stored answer from the stripped text alone (blind recovery), an independent audit confirmed that problem-specific data were intact and the method remained unambiguous, and a second, independently developed model also reproduced the answer. The de-scaffolded statements are the released problem texts, and they are the statements read at the final review gate, at which a domain expert inspected the statement, the reference solver and the stored answer of every one of the 436 problems and approved each one before release.

**Annotation and composition.** Each released problem carries a ten-class subject category, assigned by two-vendor consensus re-identification with adjudicated disagreements, and an intrinsic difficulty grade (low, medium or high) from a rubric-based score by a reasoning model; annotations play no role in admission. The final core set comprises 436 problems drawn from the thirteen textbooks, with 734 graded sub-answers in total; 298 problems (68.3%) ask for a single quantity and 138 ask for two or more, up to fourteen.

## Perturbation families

Each core problem is paired with two certified perturbation families that hold the physics fixed (Fig. 3). Their construction shares one governance pattern: Claude Opus 4.8 writes, and models from the other two developers review.

**Parameterization.** Before any perturbation, every solver parameter was typed by role: stated in the problem text (and therefore perturbable), used but not surfaced, or a physical constant. A structural transformation then demoted every physical constant from the solver signature to a named local variable, with the output proven bit-identical before and after, so that variant generation cannot alter a physical constant even by accident.

**Numeric variants (contamination probe).** New input values were drawn programmatically for text-stated parameters only, under layered machine-checkable gates: a perturbed value had to appear verbatim in the regenerated statement, had to propagate to a non-trivial change in the solver output (rejecting solvers that ignore their inputs), and could not alter units or the set of asked sub-questions. Claude Opus 4.8 rewrote the statement around the new values, and the variant ground truth was obtained by executing a full-precision twin of the reference solver, freed of the textbook's own rounding, at the perturbed point. Of the 436 core problems, 346 admit safe perturbation and carry five numeric variants each (1,730 variants); the remaining 90 are retained core-only because re-sampling their inputs would not yield a well-posed twin (inputs compressed into constants by the phrasing, methods that cross a regime boundary under perturbation, answers non-smooth or identically zero in the inputs, or no free scalar).

**Paraphrase variants (linguistic robustness probe).** Five rewordings per core problem (2,180 variants) were generated with numbers, solver and answers held fixed. A deterministic fidelity gate required that every stated magnitude survive the rewrite and that the token-level edit ratio exceed a threshold, ensuring genuine rephrasing rather than a near-copy.

**Certification.** Every variant of both families passed three further stages (Fig. 3, bottom). First, automated rule-based checks: a solver-faithfulness audit (detection, by abstract-syntax-tree inspection and input perturbation, of answer values baked in as literals and of dead inputs) and a question-order alignment check (the order of asked quantities in the statement must match the order of the stored answers); anything flagged was repaired or removed and then re-verified. Second, cross-model verification as the final backstop, by the two developers other than the author (GPT-5.5 and Gemini 3.1 Pro): for numeric variants both had to reproduce the recomputed variant answer by solving blind, and for paraphrase variants both had to agree that the rewording poses the same problem, with the stored answer still uniquely correct; a failing variant was regenerated and re-verified rather than patched. Third, a final expert review in which every automated or cross-model flag, together with a random sample of accepted variants from both families, was re-checked by hand by a domain expert, who decided in each case between repair, regeneration and removal. The evaluated corpus therefore comprises 4,346 instances derived from 436 distinct problems.

## Diagnostic probe sets

Two held-out probe sets extend the corpus; neither enters the leaderboard denominators.

**Scaffolding ablation.** For the 169 core problems whose original statements handed over recallable formulas or constants and whose released text is byte-identical to the stripped form, the pre-strip originals were preserved and paired with their stripped counterparts. The reference solver and answers are identical across the two versions, so running a model on both isolates the scaffolding effect (accuracy with versus without the handed-over knowledge) from intrinsic difficulty. Each retained rewrite had already passed the blind-recovery gate above, establishing that the stripped problems remain well posed and solvable, only harder. Four models spanning the capability range, each in its non-reasoning setting, were evaluated on both versions under the code protocol, three runs per condition, with paired outcomes summarized under a majority-of-three rule.

**Trap problems.** A trap is a single-trigger perturbation of one certified core problem in which a stated condition invalidates the problem's own canonical method, so that the reflexive formula returns a specific wrong value while careful physical reasoning yields a different, correct one. Traps were sourced two ways: by mining stored evaluation results for core problems on which several strong models fail with outputs clustering on one wrong value, and by authoring regime, definition or sign triggers into clean core problems and recomputing the correct answer. Each candidate passed, on top of normal ground-truth certification, a deterministic separation check (the naive solver runs and its output differs from ground truth by far more than the grading tolerance; across the released set the largest per-problem separation ranges from 13% to 880%, median 65%), a fairness check (every quantity needed for the correct solution appears in the text, and a carefully reasoning frontier model recovers it, so a trap is a diagnostic rather than a test of ambiguity), and a self-containment audit; every candidate surviving these gates was then reviewed by hand for physical correctness before admission. The released set holds 67 traps, one per distinct parent, spanning six mechanism families (formula selection, 25; definition confusion, 17; sign or direction, 9; averaging in the wrong space, 9; regime boundary, 5; geometry detail, 2). Each record stores the predicted shortcut as an executable solver together with its full output vector, so that falling into the trap can be distinguished from failing for unrelated reasons; a run counts as captured only when every returned sub-answer matches the shortcut vector within 2%. The untouched parent problem serves as the built-in control. Nine configurations were evaluated (three runs each), and the headline statistic is the Trap Gap, the failure rate on traps restricted to those whose parent the same model solves in the run-matched core experiment:

$$
\mathrm{TG} \;=\; \frac{1}{R}\sum_{r=1}^{R}\; \frac{\bigl|\{\,i \in S_r : \text{trap } i \text{ failed in run } r\,\}\bigr|}{\bigl|S_r\bigr|},
\qquad S_r = \{\, i : \text{parent of } i \text{ solved in run } r \,\},
$$

which conditions out general incompetence and isolates susceptibility to the trigger.

## Comparison against an external multiple-choice benchmark

The comparison between answer formats requires content that neither protocol was designed around, so it was carried out on a published third-party benchmark rather than on our own corpus.

**Source data.** We used AtmosSci-Bench, a multiple-choice benchmark of atmospheric-science problems, in its official MCQ10 configuration: 67 problem templates, each instantiated at 10 symbolic perturbations of its inputs, giving N = 670 instances. The problems, their four answer options and their answer keys were taken as published, without edits to any statement, option or key, and were converted only in representation: each key was parsed into the value-and-unit sub-answer form our grader consumes. One template, MCQ_6, asks for two flow-type classifications alongside its numeric quantities; because a numeric grader cannot score a categorical answer, that template is graded on its two explicitly requested numeric quantities only. The conversion code and the converted file are released with this work.

**Paired dual-protocol design.** Every model was evaluated twice on the identical 670 instances. In option mode the source benchmark's own protocol was used unchanged: the model sees the four options and is graded on the letter it boxes, scored by the original authors' evaluation harness. In code mode our executable contract was used: the option list is withheld, the model returns a `solve()` function, and its executed output is graded numerically at the 5% tolerance under the same unit-aware rule applied to our own corpus. The comparison is therefore paired at the instance level and differs only in what the model is asked to produce. Two properties of the design guard the interpretation. First, the option-mode numbers are not produced by our grader, so an inflated format gap cannot be an artefact of our scoring: for three models we ran the source harness ourselves, and for three further models we quote the option-mode accuracies published by the AtmosSci-Bench authors on the same MCQ10 set, with the two groups reported separately. Second, because a strict numeric threshold could in principle depress code-mode accuracy on its own, every code-mode run was re-graded offline at 5%, 10% and 20% relative tolerance from the stored per-sub-answer values.

**Answer-key audit.** A numeric grader is only as sound as the keys it grades against, so before interpreting any code-mode result the imported set was audited with the same machinery used to certify our own corpus, and with the same conservative admission rule. Two auditor models from different developers (GPT-5.4 and Gemini 3.1 Pro) independently reviewed one representative instance per template for well-posedness, self-containedness and answer plausibility, neither seeing the other's verdict. Independently, two solver models from different developers (GPT-5.4 and Claude Opus 4.8) solved each template blind to the stored key. A template was condemned only on the intersection of both kinds of evidence, that is when both auditors flagged it and the blind solutions either agreed with each other against the key or were themselves inconsistent. A final unit-aware pass then re-examined every flag, because the blind-solve comparison is value-only: two templates whose keys are correct but expressed in a commensurate unit were retracted from the flagged set by this pass, which is the specificity control for the procedure as a whole. The intersection criterion flags 21 of the 67 templates; the unit-aware pass retracts two of them, so the audit condemns 19 templates (190 instances), of which nine carry keys that both blind solvers contradict.

**Retention and reporting.** The defective instances were deliberately retained in the evaluation set rather than removed. The option-mode accuracies published by the source authors, and our own option-mode runs, are all computed over the full MCQ10, so unilaterally discarding problems on our side would break every cross-protocol and cross-paper comparison. All results are therefore reported twice: over the full 670 instances for comparability with the published numbers, and over the 480 instances from unflagged templates for a defect-free measurement. The per-template audit verdicts and the blind solutions are released so that the flagged set can be re-examined independently. The audit is reported as evidence that unverified answer keys are a general hazard for numeric benchmarks, including our own, and it is the reason our corpus requires three-way agreement plus expert acceptance before a value is frozen.

**Exclusions.** One configuration, DeepSeek-V4-flash with reasoning enabled, is excluded from both protocols on this set. In an earlier run over the 850-instance superset from which the official MCQ10 subset was later taken, its option-mode arm returned empty responses on 201 prompts because the reasoning chain consumed the entire generation budget, leaving no tokens for the answer, and the source harness silently scores such truncations as incorrect. Since no valid option-mode arm exists for it, its code-mode arm is dropped as well so that the paired comparison stays symmetric.

## Cross-domain generalization suites

To test whether the construction method rather than the subject matter produces a discriminative benchmark, the identical pipeline (OCR, self-contained numeric extraction, blind multi-model consensus ground truth, anti-hardcode audit, machine verification) was applied to four non-atmospheric environmental domains: hydrology (37 problems; MIT OpenCourseWare courses 1.72, 1.731 and 1.060, CC BY-NC-SA), environmental chemistry (21; MIT OCW 1.85, 1.061 and 1.77), ecology and biogeochemistry (19; MIT OCW 1.018J, 1.020, 12.007 and 7.014) and soil mechanics (54; Das, Principles of Geotechnical Engineering, 9th edn), 131 problems in total. Ground truth was admitted only on position-by-position agreement, within tolerance, between the authoring model (Claude Opus 4.8) and two independent witnesses from different developers (GPT-5.5 with reasoning and DeepSeek-V4-pro with reasoning), followed by the anti-hardcode and dead-input audit; where a source ships an official answer key, stored answers were additionally cross-checked against it, and every mismatch was adjudicated by hand, separating unit and rounding conventions from genuine disagreement; problems whose official answer proved unreachable from the statement alone were removed. All 131 released solvers reproduce their stored answers under machine verification. Five non-reasoning configurations overlapping the core leaderboard were evaluated under the code protocol, one run per model.

## Evaluation protocol

**Code protocol (primary; Fig. 2).** The model receives only the problem text, with no formulas beyond those intrinsic to the statement and no expected answer, and is asked to return a `solve()` function under the same contract as the reference solvers (every given value a defaulted parameter; standard library only; explicit unit conversions; one value-unit entry per asked quantity, in order; the function must compute each answer from its parameters rather than hard-code it). The returned code is executed in an isolated subprocess with a hard 10 s timeout, and the executed output, never the prose, is graded.

**Direct protocol (comparison; Fig. 2).** The model reasons in prose using the given values and standard constants, and reports one value per asked quantity, in order, each as a boxed number with its unit, parsed by a balanced-brace scanner. The declared unit gives the grader the same unit-reconciliation ability as in code mode, so the two protocols differ only in who executes the arithmetic. The direct protocol was run on a six-configuration subset of the core leaderboard spanning the capability range and both reasoning settings (GPT-5.5, DeepSeek-V4-flash and Qwen-3.6-27B, each with and without reasoning), together with the two out-of-distribution climate models, under the same three-run design as the code protocol; every code-versus-direct comparison is therefore paired at the configuration level on the identical 436 problems.

**Prompt ablation.** Because measured accuracy can depend on how the coding task is phrased rather than on scientific competence, the code protocol was additionally run under a second, functionally equivalent prompt. The two prompts request the identical artefact, a standard-library `solve()` obeying the same return contract, and are graded identically; they differ in two coupled respects, namely the system persona (a domain expert in atmospheric science, against a Python code generator) and whether prose reasoning is permitted before the code block. The reasoning-permissive form is the default used for every other result reported here, and the code-only form is the restrictive alternative. Prompt variants are constructed by substituting fixed anchor strings in the default template, and each substitution asserts that its anchor was found, so that a mis-edit fails loudly instead of silently producing a non-variant; both templates and both system prompts are released verbatim. Four models spanning the capability range, each in its non-reasoning setting, were evaluated under both prompts on the full core set, three runs per prompt. Alongside accuracy, two mechanism-level quantities were recorded to separate a change in science from a change in executability: the fraction of problems whose returned code ran on the first attempt, and the number of problems whose code still failed to run after the full five-attempt repair budget.

**Self-repair and error handling.** A content failure, meaning the model's own output cannot be graded (code that does not run or is absent; a direct answer with no boxed value), is fed back verbatim together with the execution error or a format reminder, and the model may retry up to five times in total; output that remains ungradable is scored as a failure. A wrong but gradable answer is final and is never retried, so repair fixes format, never physics. Transient API failures are not attributed to the model: they are retried without counting and, in the rare case they never clear, the item is excluded from the denominator. One class of non-completion is scored as a failure rather than excluded. Under the direct protocol, seven records for GPT-5.5 with reasoning returned no answer at all because the in-band derivation exhausted the serving limit on the three computationally deepest problems; because the same model solves those problems under the code protocol, the non-completion is attributable to the protocol rather than to infrastructure, and these records are counted as failures and flagged as such in the released result files. Accuracy is

$$
\text{accuracy} \;=\; \frac{N_{\text{pass}}}{N_{\text{pass}} + N_{\text{fail}}}.
$$

**Runs.** Unless stated otherwise (the cross-domain suites use a single run), every reported configuration was run three independent times over the full problem set concerned, with the sampling seed offset per run; results are reported as the mean and sample standard deviation over the three runs. Sixteen configurations form the core leaderboard, and the models behind them are listed in the section Models evaluated below. Decoding parameters are fixed per configuration and recorded with the released configuration files; token accounting uses a single tokenizer (o200k) over the stored text so that counts are comparable across providers.

## Grading

Grading is answer-keyed, unit-aware and identical across protocols. Let the key for a problem list asked quantities $q = 1,\dots,Q$, each with a set of accepted values $E_q$ (multiple accepted values encode legitimate sign or convention alternatives). A returned value $a_q$ passes if

$$
\min_{e \in E_q} \frac{|a_q - e|}{|e|} \;\le\; \tau, \qquad \tau = 0.05,
$$

where zero-valued references are compared absolutely ($|a_q| \le \tau$) and signed infinities are matched symbolically. The comparison is evaluated after unit reconciliation: when both sides declare units, values are converted to a canonical form using a fixed factor table that covers compound units and offset scales (for example Celsius and Kelvin), so a correct answer expressed in a commensurate unit is not penalized. A problem passes only if every asked quantity passes. When a model keys its answers differently from the stored labels, grading falls back to positional matching in the order asked. The 5% operating point sits on a plateau: re-grading all stored runs offline at 1%, 2%, 5% and 10% leaves the ranking essentially unchanged, and the same offline re-grader reproduces the live grader's pass counts exactly.

## Statistical analysis

Problem-level outcomes are stabilized with a majority-of-three rule across runs, and a parent's variant family counts as held when at least three of its five variants are solved. Contamination and linguistic robustness are assessed on fully paired parent subsets (346 parents for numeric, 436 for paraphrase): for each model the paired shift $\Delta$ between core and variant accuracy is tested with an exact two-sided McNemar test on discordant pairs, with 95% confidence intervals from the analytic paired standard error (a seeded 2,000-resample bootstrap gives concordant intervals), and with Holm correction across the sixteen per-model tests within each family. Leaderboard stability across sets is quantified with Spearman and Kendall rank correlations. As a mechanism-level check, a failed variant answer is classified as a parent echo only when it matches the parent's textbook answer within tolerance on every graded discriminative sub-answer, a sub-answer being discriminative when parent and variant expected values differ by more than the tolerance; a problem is reported as leaked only when at least two independent models echo it while also solving the parent. Reliability is summarized as pass@3 (solved in at least one run) and all@3 (solved in all three); confidence intervals for single proportions use the Wilson score interval. Trap Gap denominators are matched run by run, as defined above.

## Human expert involvement

LLMs propose; a domain expert decides. Every stage above is gated by a human decision, and the gates are summarized here so that the division of labour is explicit rather than implied.

**Ground-truth acceptance.** Model agreement, whether against the textbook's printed answer or across three developers, never froze a value by itself. For every admitted problem an expert re-derived the agreed computation from the statement and confirmed the physics, the units and the count of asked quantities against the solver before the value was frozen (Fig. 1, Phase 2).

**Release approval.** Every one of the 436 released core problems was read in its final, de-scaffolded form by an expert, who inspected the statement, the reference solver and the stored answer together and approved the problem for release. A problem that could not be approved was repaired and re-verified or discarded (Fig. 1, Phase 3).

**Adjudication of every automated flag.** Rule-based checks and multi-model consensus reviews were used only to raise suspects, because such auditors are known to over-flag. No flag caused an automatic edit or removal: an expert examined each one and chose between repair, regeneration and removal, and any repaired artefact re-entered the verification gates from the start.

**Variant certification.** Beyond the automated and cross-model gates, an expert re-checked by hand every flagged variant together with a random sample of accepted variants from both perturbation families (Fig. 3, bottom).

**Diagnostic sets.** Each trap was reviewed by hand for physical correctness, for the fairness requirement that the correct answer be reachable from the text alone, and for agreement between the perturbed statement and its solver. In the cross-domain suites every disagreement between a consensus answer and an official course key was adjudicated by hand, separating unit and rounding conventions from genuine defects.

**External key audit.** Because the audited set is another group's published work, no template was declared defective on model evidence alone: every intersection-flagged template was inspected by hand, the retraction of the two commensurate-unit false positives was a human decision, and the flagged items were retained in the evaluation set rather than edited or removed.

**Case-level analyses.** The failure case studies reported in the Results were selected under an explicit screening protocol and each was verified by hand, either by reproducing the closed-form derivation or by confirming convergent independent solutions, before being described as a model failure rather than a dataset defect.

In the process-integrity audit of fabricated execution claims the two annotators were themselves automated, so their agreement is not human inter-annotator agreement; two domain authors subsequently reviewed every admitted record against the executed code and its replayed output and confirmed all ten, which is the verdict reported; the single record on which the automated annotators disagreed was read in full and judged honest.

## Models evaluated

Thirteen distinct models were evaluated as subjects. Nine form the core leaderboard, seven of them in both a reasoning and a non-reasoning setting, giving sixteen configurations: GPT-5.5, DeepSeek-V4-pro, DeepSeek-V4-flash, Kimi K2.6, Qwen-3.5-397B, Qwen-3.6-27B and Qwen-3.5-9B in both settings, Gemini 3.1 Pro in its reasoning setting and Qwen-2.5-72B-Instruct without one. Two domain-adapted climate models, ClimateGPT-13B and ClimateGPT-70B, were evaluated under both protocols as an out-of-distribution reference and are excluded from all leaderboard aggregates. Two leaderboard models, GPT-5.5 and Gemini 3.1 Pro, also served as verification solvers during construction, and the cross-domain consensus witnesses are reasoning settings of two leaderboard backbones. This overlap is disclosed rather than hidden, and three properties bound its effect: most problems are anchored to the textbook's printed answer rather than to model agreement; on the cross-model route the selection effect runs one way only, in that admission required the verifiers to solve a problem at certification time, which is stated as a limitation; and the evaluated statements are the de-scaffolded rewrites, not the texts the verifiers saw, with the numeric-variant family probing directly for any residual familiarity advantage.
